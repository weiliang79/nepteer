# Step 6B.8 — Steam Deck Tools GPU temperature acquisition and privilege analysis

Research date: 2026-11-28. Branch: `research/steam-deck-tools-gpu-temperature-path`.
Final decision: **D — No reliable end-to-end acquisition path established for the observed installation.** The release provider exposes credible ADL candidates, classified **B — standard-user support plausible but unverified** independently of the unresolved display lookup. No diagnostic implementation or physical execution is authorized.

## 1. Executive summary

Performance Overlay requests elevation unconditionally in its application manifest, and its project explicitly embeds that manifest. Static inspection of the official 0.7.4 portable apphost confirms the same active `requireAdministrator`, `uiAccess=false` element. The kernel-driver menu item changes runtime state; it does not change the manifest or process token. Consequently the UAC prompt establishes an application requirement, not a GPU getter permission requirement. [S1, S2, W1]

The shared monitor has other privileged capabilities: a Valve helper using InpOut, CPU monitoring described as requiring RyzenSMU, and, in the likely matching LibreHardwareMonitor source, unconditional Ring0 initialization at `Computer.Open()`. Disabling the menu option is **not proof that the complete process avoids custom drivers**. None of these observations proves that the AMD temperature getters themselves need those facilities. The inspected AMD temperature methods call the installed AMD ADL runtime rather than Ring0/InpOut. Existing AMD display-driver kernel execution is a separate dependency from installing a monitoring driver. [S3, L2–L4]

There is a material unresolved lookup discrepancy: the overlay selects a temperature sensor named `GPU Temperature`, but LibreHardwareMonitor v0.9.1 constructs `GPU Core`. The official NuGet net6.0 DLL has the latter UTF-16 string and lacks the former; the official Steam Deck Tools 0.7.4 archive ships exactly those DLL bytes. Its overlay contains both strings, consistent with separate clock and temperature lookups, not evidence of a temperature fallback. No sensor rename or fallback connecting these names is established in the inspected path. This does not refute the user's reading; it prevents identifying their installed acquisition chain from this release alone. [S4, L1, L2]

The likely corresponding release source uses legacy `ADL_Overdrive5_Temperature_Get`, then conditionally `ADL2_OverdriveN_Temperature_Get`, then conditionally `ADL2_New_QueryPMLogData_Get`. It does **not** use current upstream's ADL2 OD5/GFX fallback path. No static branch analysis reveals which native call succeeded on the user's hardware. No ordinary-user target result or applicable permission guarantee was found. Licensing gates from 6B.7 remain. [L2, L5, A1–A3]

**One recommended next action:** reconcile the observed installation's provenance through a narrowly scoped, read-only version/file-hash and matching-source review, without launching monitoring or changing settings. Identify the installed Steam Deck Tools version/build and hashes of PerformanceOverlay.exe, PerformanceOverlay.dll, CommonHelpers.dll and LibreHardwareMonitorLib.dll against official archives; if different, obtain their authoritative corresponding source/provenance. Resolve the temperature lookup before selecting any diagnostic getter. This is the next investigation, not authorization for a hardware test or new executable.

## 6. Kernel-driver option and initialization behavior

`CommonHelpers.Instance.HardwareComputer` initially enables CPU, GPU, memory, storage and battery. `Controller` calls `Instance.Open` with the saved kernel-driver preference. A changed `UseKernelDrivers` value opens/closes `Vlv0100`, sets `HardwareComputer.IsCpuEnabled` to that value and resets hardware groups. GPU/memory/storage/battery flags are not disabled by that setter. The comment associates CPU monitoring with RyzenSMU. [S3]

**Startup caveat:** the backing flag initially equals false and the setter returns immediately on an equal value. On an initial false request, its CPU-disabling assignment is therefore skipped even though the static CPU flag starts true. A true-to-false transition does disable the CPU group. The code does not support the blanket statement that every disabled-option startup suppresses CPU SMU access. This is an upstream research observation; Nepteer does not fix or reproduce it.

`Vlv0100.Open` constructs an InpOut helper and reads firmware/board data; closing the option closes this helper. These operations are distinct from ADL GPU temperature. In likely matching LHM source, `Computer.Open()` calls `Ring0.Open()` before adding enabled groups, without checking the Steam Deck Tools setting. `Computer.Reset()` removes/recreates groups; it does not close Ring0. `Ring0.Open()` attempts an existing driver handle, then extraction/installation/opening of WinRing0 if needed, with retry logic. An unsuccessful Ring0 open leaves its driver null rather than explicitly gating AMD group creation. [S3, L3, L4]

Thus the option is not a comprehensive disable switch for all privileged library initialization in the reviewed architecture. Actual driver installation, successful opening or continued access on the user's device is **unknown**. No installed-service inventory or driver inspection was performed. The package contains embedded driver resources, but resource presence alone proves neither use nor necessity for temperature.

## 8. Overlay sensor lookup and conceptual data flow

Verified source chain, with the unresolved boundary explicit:

1. `Program.Main` creates the overlay controller. `Instance.Open` opens the shared LHM computer.
2. When RTSS/OSD is available and ShowOSD is true, a Windows Forms timer normally runs at 250 ms. `Sensors.Update` acquires a shared mutex with a 200 ms wait, calls each hardware group's `Update`, collects sensors and stores that list. Exceptions can be suppressed and mutex admission can fail. This is scheduling, not sample-age evidence. Hidden OSD uses a 1000 ms timer interval and returns before the sensor update; missing RTSS also returns early.
3. Overlay templates use `GPU_T`. Its `HardwareSensor` searches the collected sensors for type `GpuAmd`, a recognized GPU-name prefix (including `AMD Custom GPU 0405`), temperature type and exact name `GPU Temperature`. It returns the **first matching sensor**, even if that sensor has no value, rather than trying later matching sensors for a valid reading.
4. A non-null, nonzero value is formatted with one decimal in en-US culture. Zero is suppressed by `IgnoreZero`; no calibration, age or finite/range policy is added there. Missing entries can be omitted by overlay templates.
5. Likely corresponding LHM source registers temperature index 0 as `GPU Core`, with separate memory/VR/liquid/PLX/hotspot sensors. This is the unresolved lookup boundary. LHM supports sensor renaming through settings, but this overlay instantiates the default computer and no applicable rename is established in the reviewed path. The release-source SensorVisitor only traverses and invokes the supplied collector; it does not supply a rename.
6. That LHM core sensor can be populated by the ADL branches below, through `atiadlxx.dll`. AMD documents ADL binaries as display-driver supplied. Communication onward through the existing AMD display stack is the architectural inference; its private kernel/firmware implementation was not inspected.
7. A particular native value reaching this user's display is **not traced**. No return value, runtime branch, rename, source customization or actual loaded DLL is known. [S3–S5, L1–L3, A1]

`GPU Core` also names a **clock** sensor. Matching sensor type prevents that clock from becoming temperature; utilization, frequency, power and thermal limits are never temperature substitutes. The current mismatch must not be “resolved” by assuming the two temperature labels are interchangeable.

## 9. AMD identification, initialization and ownership

The following is the **v0.9.1 release-source path**, likely corresponding to the identified DLL; full IL equivalence was not verified. `AmdGpuGroup` initializes legacy global ADL with its allocation callback and connected-adapter enumeration, obtains adapter count/info and records active/ID information. Admission requires a nonempty UDID and AMD vendor identity; recording activity is not the same as rejecting inactive adapters. Candidates are grouped by bus/device and the candidate with the largest exposed sensor count is retained. This heuristic is not Nepteer's required unique-target policy. [L2]

`AmdGpu` retains adapter index/bus/device and trimmed adapter name. It queries `ADL_Overdrive_Caps`, storing support and API version; the returned enabled flag is not used as an independent temperature gate. Capabilities failure leaves API level -1. At level >=5, if the export exists, it attempts `ADL2_Main_Control_Create`; failure zeros the context. The inspected source passes the adapter index in the second argument position of that initializer. AMD's documented argument there is connected-adapter enumeration, not adapter identity: do not translate this sequence into a recommended consumer contract. Context absence is not a universally enforced stop before later calls. [L2, A2]

The provider also initializes unrelated frame metrics and a write-capable fan control and performs an initial `Update()`. Teardown detaches control handlers, may restore fan defaults depending on control mode, stops frame metrics if started and destroys a nonzero ADL2 context; the group later destroys global ADL. Group close catches exceptions. These are source ownership observations, not guaranteed successful cleanup or a safe read-only wrapper. Nepteer must not reuse this broad initialization/update/teardown sequence. A future original consumer needs a separately verified allocator, context and partial-failure cleanup contract with no tuning, fan writes or tracking sessions. [L2]

## 10. Possible temperature branches and exact precedence

| Order and runtime condition                    | Native method in v0.9.1 source                                            | Result affecting core temperature                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| First, if Overdrive support flag is true       | **`ADL_Overdrive5_Temperature_Get`**, adapter index, thermal controller 0 | Exact ADL_OK sets core from millidegrees ×0.001; failure clears core to null                                            |
| Next, if support true and API level >=7        | **`ADL2_OverdriveN_Temperature_Get`**, EDGE selector, context and adapter | Accepted success overwrites core; failure/out-of-range preserves prior core (`reset=false`)                             |
| Last, if API level >=8 **or support is false** | **`ADL2_New_QueryPMLogData_Get`**, if export exists and returns ADL_OK    | A supported PMLOG_TEMPERATURE_EDGE entry overwrites core; absent/unsupported entry preserves prior core (`reset=false`) |

This is sequential overwrite precedence, **not** “try another getter only when the previous getter fails.” Capabilities failure can select PMLog through support=false. A level-8 device can execute all three branches. Other temperature fields have their own reset policies; they are not folded into core. PMLog SoC and hotspot are separate sensors. No GFX fallback is present in this release source. [L2]

**Not used as temperature getters in this version:** `ADL2_Overdrive5_Temperature_Get` and `ADL2_Overdrive6_Temperature_Get`. Its OD6 calls acquire power, not temperature. The absence of these methods from this update path is not a claim the AMD SDK lacks them. No static inspection selects the successful getter on the physical Deck.

## 11. Temperature semantics, errors and freshness

| Source                        | Meaning/units supported by evidence                                                                                        | Admission and limitations                                                                                                                                                                                                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OD5                           | AMD `ADLTemperature.iTemperature` is millidegrees Celsius for the selected thermal controller; release source scales 0.001 | Exact success only, but no release-source temperature range/sentinel check; generic GPU/controller temperature does not establish edge versus hotspot on this APU                                                                                                                                    |
| Overdrive N EDGE              | LHM applies EDGE selector 1 and scales millidegrees by 0.001                                                               | LHM bounds raw to -256000..256000 inclusive. These are library heuristics, not silicon limits or proof of validity. Its interop comment admits the enum mapping is inferred because AMD documentation names but omits that enum; independent authoritative selector/unit confirmation remains a gate |
| PMLog edge                    | AMD documents PMLOG_TEMPERATURE_EDGE as current die-edge temperature in Celsius; LHM uses factor 1                         | Requires successful query and nonzero per-entry supported flag/bounds; no generic temperature plausibility or sentinel filter. Separate fan ushort sentinel handling is not a temperature contract                                                                                                   |
| Current upstream GFX fallback | Separate PMLOG_TEMPERATURE_GFX value can fill the same core sensor only in the newer comparison source                     | GFX is not automatically edge, CPU Tctl/Tdie or HWiNFO APU GFX; absent from the 0.9.1 core path                                                                                                                                                                                                      |

The Overdrive N range filter can still admit a plausible invalid value, and scaling/range alone is not a validity contract. No universal AMD invalid sentinel is established. The overlay hides zero without proving whether zero is a sentinel; it does not independently validate nonzero numbers. No values were acquired here. [L2, L5, A2, A3]

No per-core-temperature timestamp is checked by this release path. `Sensor.Value` returns its stored current value; its history averaging is separate and is not what the overlay reads. If a PMLog-only update fails, prior core state can survive because it is not reset at the beginning of every update. OD5 failure clears core when that branch runs; N/PMLog failure with reset=false preserves earlier results. Skipped timer/mutex updates, swallowed exceptions and underlying driver caching can also leave an old displayed value. A 250 ms timer and a plausible changing number do not establish sample freshness. No polling or retry is proposed for Nepteer.
