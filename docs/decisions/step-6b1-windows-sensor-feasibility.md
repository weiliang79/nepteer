# Step 6B.1 — Windows sensor discovery and feasibility

Research date: 2026-11-27. Status: proposed decision for review; no sensor implementation or hardware discovery executed. Branch: `research/windows-sensor-feasibility`.

## 1. Executive summary

**Retain unavailable CPU/GPU temperatures and fan RPM in production.** No reviewed source establishes a correctly attributed, current, ordinary-user reading for Steam Deck LCD + Windows 11 + the user's installed Valve APU driver. This is an evidence gap, not proof that the hardware cannot measure them.

GPU temperature is the best first **investigation**, using Microsoft's documented `D3DKMTQueryAdapterInfo` / `KMTQAITYPE_ADAPTERPERFDATA`. It provides adapter temperature and fan fields, but their availability and physical meaning on this APU remain unknown. AMD ADLX is a documented alternative with explicit per-metric support discovery; Deck/Valve-driver compatibility and SDK licensing remain gates. Neither source authorizes CPU temperature attribution or Deck system-fan attribution. [M5–M8], [A1–A4]

CPU: WMI temperature-probe metadata is not a live CPU thermometer. ACPI thermal zones may describe board/skin/aggregate zones rather than CPU silicon. Fan: requested speed is not measured RPM; an ACPI status method is not automatically an application API. Tools displaying readings do not establish a safe independent backend. Defer both pending better evidence. [M1–M4], [F1–F3]

Recommended Step 6B.2: manually establish the non-sensitive driver/OS context, then separately approve a bounded, optional, GPU-only feasibility experiment using documented OS queries. Keep production capabilities false until support, attribution, freshness and lifecycle acceptance are met. No sensor is ready for unconditional implementation.

## 2. Objectives and decision rule

Evaluate CPU, GPU and fan independently: API contract, target support, ordinary-user access, physical attribution, dependencies/licenses, latency, privacy and failure behavior. A supported path, installed sensor, successful numeric return and validated physical measurement are four different claims. Prefer unavailable to an unsupported, misidentified or unsafe value. This document proposes future work; it does not authorize new commands, device access or experiments.

## 3. Existing Nepteer architecture (repository facts)

Audited at main `8d54db41b8995274ccbe37f57257988bb38dd08f`: `src-tauri/src/{lib.rs,telemetry.rs,telemetry/windows.rs}`, `src/lib/{telemetry.ts,bindings.ts}`, `App.tsx`, `QuickAccess.tsx`, their tests, command permissions and both capability files, under `apps/desktop/`.

- `getTelemetry()` invokes the typed `get_telemetry` command. Browser preview rejects missing Tauri rather than supplying fake telemetry. Rust copies session `ProviderMode` under a short mutex, releases it, then runs `provider_for(selected).snapshot()` with Tauri `spawn_blocking`. No controller-reader or QAM coordination lock is held by this path.
- Only main may pass a provider mode. Automatic uses Windows on Windows and mock on other hosts; explicit mock is session-only. Rust emits `provider-changed` to QAM. Restart defaults to Automatic; failure never switches to mock. Theme/units are separate saved frontend preferences.
- Windows reads `GetSystemPowerStatus`, then a local `ROOT\CIMV2` WMI query selecting exactly `Manufacturer, Model FROM Win32_ComputerSystem`. Each request creates, uses and drops its connection on the same blocking worker. Existing `wmi` 0.18.4 initializes COM as needed; its standard enumeration uses `Next(WBEM_INFINITE, ...)`. The request can block indefinitely; there is no native telemetry timeout, cancellation or cross-window single-flight gate. This is an existing limitation, documented here without a fix. [R2], [M10]
- Battery/identity failures are independent. Successful fields survive partial failure; sanitized `issues` avoid raw WMI errors/identifiers. Source remains `windows`. A timestamp failure or worker failure can reject the whole request. Battery has a separate status enum; temperature/fan do not.
- Windows temperature/fan values are all `None`, with CPU/GPU/fan and hardware-controls capability booleans false. Mock has fixed CPU 54°C and fan 2800 RPM, GPU unavailable, battery 78%; those remain simulated. Capability currently means implemented read support, not successful current reading (battery remains true on a failed battery read).
- `Snapshot` already contains `Option<Celsius>` for CPU/GPU and `Option<Rpm>` for fan. `Celsius::new` requires finite −273.15 through 200 inclusive; this broad representational range is not a plausibility test for an operating CPU. `Rpm` wraps `u32` without a sensor-specific range check. Zero survives serialization/tests.
- `timestamp()` uses `SystemTime` since Unix epoch in milliseconds at snapshot assembly, after reads. It is retrieval time, not sensor acquisition time, freshness proof or a monotonic deadline. Earlier battery and later WMI results are not simultaneous samples.
- Dashboard requests on mount/provider selection/manual refresh, fences obsolete completions through effect cleanup, and clears readings on manual refresh. Cards check capabilities/null; temperatures are rendered from Celsius using `Math.round`, Fahrenheit = Celsius × 9/5 + 32. Source labels distinguish LIVE WINDOWS/MOCK DATA; partial issues remain visible. Shared unit preference changes formatting only.
- QAM requests on genuine native open, provider change and manual refresh; sequence/alive fences discard hidden/obsolete results. Busy controls prevent duplicate manual reads, but provider/open events can supersede requests. Native work already started is not canceled. QAM currently displays battery, source and issues, **not CPU/GPU/fan cards**. Settings changes shared theme/units without adding sensors. Navigation claim/complete does not await telemetry or the retained diagnostic delay.
- Both native window capabilities grant generated `allow-get-telemetry`; the command separately rejects QAM mode arguments. QAM has no device-management permission. New internal sensor reads could fit this provider/DTO/command structure without new frontend permissions or commands; Windows API binding features might still require separate dependency review. Tauri command permission is not Windows hardware access authorization.
- Rust tests cover units/zero/invalid values, fixed mock, provider selection, synthetic power/identity failures and binding drift; `lib.rs` tests enforce window/provider boundaries. Frontend telemetry/App tests cover wrapper/browser rejection, source, partial failures, null/zero, capability gating, retry and unit rendering. QAM tests cover shared provider, visibility, stale results, duplicate protection and focus. These do not establish physical sensor support or native WebView2 behavior.

## 6. CPU temperature findings

`Win32_TemperatureProbe` in `ROOT\CIMV2` exposes SMBIOS-derived metadata. Microsoft explicitly says current WMI implementations do not populate `CurrentReading`; its schema/unit does not supply a working CPU read. Reject it for live CPU temperature. [M1]

`MSAcpi_ThermalZoneTemperature` in `ROOT\WMI` is a candidate firmware-zone discovery path, not a CPU API. Microsoft documents the Windows thermal framework, zone/device relationships and tenths-Kelvin temperature model; existence/access/updates on this Deck remain unverified. A zone may aggregate heat or protect the enclosure. Neither a name containing CPU nor a plausible 50°C proves CPU-die attribution. Do not select the first/hottest zone or infer CPU and GPU from the same APU value. [M2], [M3]

The expected zone conversion is °C = raw / 10.0 − 273.15; validate the actual provider/property units before applying it. Plain Thermal Zone Information performance-counter temperature is in **Kelvin**, so °C = K − 273.15, without dividing by ten. Do not reuse one conversion for every Windows sensor class. `Win32_TemperatureProbe.CurrentReading` describes tenths Celsius but is not populated. [M1–M3]

Ordinary-user WMI is possible only where namespace ACLs and provider checks permit it; `ROOT\CIMV2` identity access does not prove `ROOT\WMI` access. Permission denied, absent class, no instances and ambiguous zones are distinct discovery outcomes. No ACL changes or elevation fallback. Scalar projection can omit hostname, serial, UUID and instance paths, but also removes convenient attribution information; missing attribution must remain unresolved. [M4]

AMD Ryzen Master Monitoring SDK is explicitly read-only and lists Ryzen/Threadripper scope, not explicit Deck custom-APU support. Its page warns about SMU request frequency and concurrent similar tools. Required runtime/driver privileges and redistribution terms have not been established for this target; read-only marketing is not proof of a driver-free path. Defer, and reject MSR/SMU/register workarounds under this milestone. [A5]

## 7. GPU temperature findings

GPU utilization, engine activity and video-memory usage do not imply thermal measurement. Microsoft's Task Manager architecture describes VidSch/VidMm scheduling/memory statistics; DXGI `QueryVideoMemoryInfo` returns memory budgets/usage, not temperature. Do not derive temperature from load, clocks, memory or power. [M9], [M11]

The strongest OS candidate is `D3DKMTQueryAdapterInfo` with `KMTQAITYPE_ADAPTERPERFDATA` and `D3DKMT_ADAPTER_PERFDATA`. This is a documented Gdi32 user-mode entry point backed by the existing display stack, not an instruction to open arbitrary device IOCTLs. Its interval-collected adapter data includes temperature in **0.1°C**, fan RPM, and power in **0.1 percent**, not watts. Temperature conversion is raw / 10.0. Static `ADAPTER_PERFDATACAPS` limits are not current readings. The caps structure documents Windows 10 1803/WDDM 2.4 minimum; the generic query's Vista minimum does not guarantee this later query type or driver fields. [M5–M8]

No target-specific Valve contract or physical evidence establishes these fields. Microsoft's temperature description is a main adapter sensor, not an explicit junction/hotspot contract. Fan field semantics do not establish Deck system-fan identity. Standard-user access is the proposed test condition; the docs list no elevation requirement, but that is not a successful target test. Return status success alone does not distinguish a real zero from an unimplemented field. Do not treat nonzero as proof either. [M5], [M6]

An independently written Rust FFI wrapper around a small documented read-only query is plausible. Before any experiment, verify SDK structure layout/alignment, exported functions, matching handle ownership and query-type support; keep adapter LUIDs private and ephemeral. Do not copy community hard-coded ABI declarations or assume adapter zero. Runtime support, units, sample age, failure semantics and attribution need acceptance before populating `gpuTemperatureCelsius`.

## 8. Fan RPM findings

`Win32_Fan.DesiredSpeed` is requested RPM; Microsoft explicitly points to an associated `CIM_Tachometer` for actual speed. A schema relationship does not guarantee a dynamic provider/instance or usable current reading on Deck. No such Deck provider was established. Do not show DesiredSpeed, PWM percentage, maximum RPM or an active-cooling boolean as measured RPM. [F1]

ACPI `_FST` optionally reports actual RPM and defines `0xFFFFFFFF` as unsupported speed reporting. Firmware implementation and a supported application-facing Windows provider are both unknown. Microsoft's ACPI method-evaluation documentation concerns KMDF/WDM and Windows 8+ UMDF **drivers**; UMDF support does not turn arbitrary AML evaluation into an ordinary desktop application API. Do not add an ACPI bridge or evaluate vendor methods. [F2], [F3]

D3DKMT/ADLX GPU fan metrics are worth documenting but cannot be assigned to the Deck's shared cooling fan without a target contract. No reviewed official Valve application API establishes LCD system-fan RPM. If only EC, SMBus/I²C, port I/O, privileged handles, PCI/MSR/SMU access, firmware commands or monitoring drivers can obtain it, defer behind a separate architectural/security decision. No addresses or probing procedure are proposed.

## 9. WMI/ACPI and other Windows sensor interfaces

Windows 11 retains WMI/CIM and the documented Windows thermal model, but class availability, instances and populated values depend on firmware/provider/permissions. Generic CIM sensor/tachometer classes model data; they do not install a sensor backend. Thermal-zone performance counters are another view of zones, not a second independent CPU thermometer. Firmware updates, sleep/resume and driver versions may change behavior. [M1–M4], [F1–F3]

Windows sensor frameworks likewise require a driver exposing the relevant sensor type; no reviewed official source established CPU/GPU/fan publication through such a provider on Deck LCD. This is an unresolved alternative, not a selected integration. Do not enumerate arbitrary namespaces/devices or export full WMI/ACPI/SMBIOS inventories to search for it.

## 10. AMD/Windows API assessment

ADLX 2.0 (September 2026) documents GPU performance monitoring on Windows 10+ with a compatible AMD driver. `IADLXGPUMetricsSupport::IsSupportedGPUTemperature` and fan support are independent checks (minimum API 1.0); each read must also succeed. `GPUTemperature` is edge temperature in °C, distinct from hotspot/intake temperature. Do not silently substitute hotspot or CPU package values. Compatibility guidance warns older drivers can expose reduced interfaces. It does not explicitly establish support for Valve's custom APU/2023 LCD driver. [A1–A4]

ADLX is a user-mode SDK talking to an AMD driver already on the system. No separate kernel helper is selected, and actual ordinary-user initialization on this target remains unknown. Reject incompatible-driver initialization workarounds or driver replacement. A future evaluation would need per-metric discovery, a one-shot metrics method, SDK reference-count cleanup, and exact licensed runtime/loading review; no tuning, I²C, process-list or control interfaces.

Legacy ADL documents Overdrive temperature/fan getters, but hardware/Overdrive-version support must be checked independently. Desktop Radeon support is insufficient. ADL is not preferred for new work; the reviewed legacy SDK EULA has distribution/notice restrictions and must not be confused with an unrelated MIT wrapper. ADLX has its own SDK agreement, not blanket GPUOpen MIT terms. No SDK/header/library is added here. [A6], [A7]

## 13. Security and licensing risks

No new access is selected for production. A documented user-mode query still depends on a kernel display driver, but does not require Nepteer to install a monitoring driver. Conversely, putting a privileged collector behind WMI/shared memory does not satisfy a no-driver architecture. Assess the entire acquisition chain.

EC/register/bus/MSR/PCI probing, private AMD calls, arbitrary IOCTLs, kernel monitoring drivers, privileged services, driver replacement, firmware/control commands and elevated helpers require a separate security/architecture decision. Read-only intent can still require writes to select registers or perform bus transactions; it is insufficient safety evidence. No fan/clock/power manipulation, exclusive ownership, controller changes, remote telemetry or persistent history is proposed.

For an external publisher, treat shared memory/WMI contents as untrusted: validate version, lengths, counts, offsets, units, sensor identity and finite bounds; handle concurrent updates and producer exit. Do not trust a sensor name or index alone. Prove the license permits the exact integration; optional user installation does not waive SDK obligations. HWiNFO bundling requires approval and limits must not be bypassed. MPL/component obligations and privileged drivers remain separate questions. ADLX license text extraction was unavailable, so redistribution approval is **not established**. These are engineering gates, not a legal opinion. [T1–T8], [A7]

## 14. Performance and lifecycle proposal

Preserve snapshots; no polling daemon, periodic refresh, monitoring service or automatic retry. COM objects must be created/used/released in their owning apartment/thread; do not carry WMI objects across awaits/worker boundaries. Existing blocking workers keep frontend/event-loop execution free but do not bound OS/driver latency. [R2], [M10]

Before adding a sensor: measure one-shot elapsed time manually on the exact driver, cap enumeration/result sizes and admit at most one sensor acquisition with bounded pending work across dashboard/QAM. Do not retain a controller lock while waiting. Multiple refreshes, provider changes, hide/reopen and shutdown must invalidate result publication without pretending to cancel an in-progress synchronous OS call.

WMI semisynchronous enumeration offers `Next` timeouts, but that does not automatically bound connection/provider initialization or kill a hung call. D3DKMT query docs provide no caller timeout. A JavaScript promise timeout or dropping a join handle is not native cancellation. Require a separately reviewed admission/cleanup policy before enabling either; do not spawn unlimited replacement workers. A stuck request should cause subsequent sensor attempts to fail closed, with the shutdown limitation stated honestly. A process-isolation solution would be a separate architecture proposal, not an automatic addition. [M5], [M10]

Use RAII to release adapter handles/COM/SDK references on every normal/error path; never close resources still in use by an outstanding call. Keep provider generation and UI stale-result fences; distinguish monotonic elapsed time from wall-clock retrieval time. No battery/CPU overhead measurements were made; include them in acceptance, especially the producer's own sampling for third-party APIs. No always-running SDK tracking/history by default.

## 15. Data correctness and uncertainty

Existing nullable values, support booleans and sanitized issues suffice for conservative **single-source validated current readings**. They cannot express per-sensor provenance, acquisition age, presence, ambiguous attribution and error categories in a typed way. Keep DTOs unchanged now. If a future source cannot establish freshness without those fields, propose a separate status extension before enabling it; never hide ambiguity behind a number.

| Condition                            | Future required behavior                                                                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API unavailable / unsupported driver | Capability false for unsupported read path; null; sanitized reason; no mock/driver fallback                                                                                        |
| Supported read path, sensor absent   | Distinguish internal absence from read failure; null, not zero; never claim physical presence from support alone                                                                   |
| Permission denied                    | Null and sanitized access issue; no elevation, ACL change or helper                                                                                                                |
| Invalid / non-finite / out-of-range  | Null, no clamping; apply source-specific validity and plausible operating limits before Celsius/Rpm construction                                                                   |
| Numeric zero                         | Preserve genuine documented zero (including stopped fan); reject only documented sentinel/invalidity. Unknown zero semantics → unavailable, not arbitrary universal zero rejection |
| Outside plausible CPU/GPU bounds     | Null even if DTO accepts it; define bounds from selected sensor contract, not guessed fixture values                                                                               |
| Stale / no freshness evidence        | Do not relabel cached data as current using retrieval timestamp. Frozen values alone do not prove staleness; absence of change alone does not prove freshness                      |
| Device changed/disconnected/sleep    | Invalidate cached support/selection and pending results; return null until revalidated; no silent migration to another adapter                                                     |
| Slow response                        | Bounded admission; report unavailable/pending honestly; late result cannot overwrite a new provider/open/request                                                                   |
| Partial failure                      | Preserve battery/device and other independently valid values; per-sensor issues; no whole-snapshot fake fallback                                                                   |
| Conflicting APIs                     | Do not average, choose plausible/hottest or silently substitute edge/hotspot/package. Resolve identity/units/time; otherwise null                                                  |
| Unsupported GPU or fan               | Keep each field/capability independent; one working GPU metric authorizes neither CPU nor fan                                                                                      |

A future capability true would mean the approved backend supports the metric for the validated configuration, not continuous accuracy, universal hardware support or successful current sampling. Physical validation should establish attribution plus bounded behavior; it cannot calibrate silicon-sensor absolute accuracy without a reference standard. Record that limit.

## 16. Proposed safe manual physical discovery

**Pending; no queries or device experiments were run.** This procedure authorizes observation only, not new production access. Use the ordinary desktop account, no active game. Do not install software/drivers, elevate, disable protections, change firmware or alter Steam/Steam Deck Tools configuration. If any step requests elevation or a driver, cancel that step and record unavailable.

1. Confirm LCD model from the user's known device, Windows 11 version/build in Settings → System → About (transcribe only version/build). In Device Manager → Display adapters → existing AMD adapter → Properties → Driver, transcribe provider, version and date only. Do not copy device-instance paths, hardware IDs, account name, serial/UUID or a full system report. Optionally view WDDM version in the existing DirectX Diagnostic Tool display tab; do not save/export its report.
2. View Task Manager → Performance → GPU. Record whether an explicitly labeled temperature exists and its unit/category. Absence does not prove D3DKMT absence; utilization and memory graphs are not temperature evidence. Do not install/update a driver to obtain it.
3. If a trusted monitoring app is **already running and configured**, inspect its existing sensor view only. Do not start a new monitoring tool, enable additional EC scanning/sharing, change fan mode or accept an install/elevation dialog. Record app/version, exact sensor display name, category (CPU package/edge/hotspot/system fan/unknown), unit and numeric-present yes/no. Values are optional manual observations, not a history export. Record a documented provider/API only when known; otherwise write unknown.
4. Optionally run each narrow query below **once**, in ordinary Windows PowerShell. These use local OS WMI only; never use `SELECT *`, full inventory exports, remote sessions or administrator retry. `-OperationTimeoutSec` limits the requested CIM operation; it is not a promise of hard provider cancellation. If slow/hung, stop and record inconclusive; do not repeatedly launch queries. They deliberately omit unique instance paths, so they cannot prove attribution.

```powershell
Get-CimInstance -Namespace root/wmi -Query 'SELECT Active, CurrentTemperature FROM MSAcpi_ThermalZoneTemperature' -OperationTimeoutSec 5 -ErrorAction Stop | Select-Object Active, CurrentTemperature
Get-CimInstance -Namespace root/cimv2 -Query 'SELECT CurrentReading FROM Win32_TemperatureProbe' -OperationTimeoutSec 5 -ErrorAction Stop | Select-Object CurrentReading
Get-CimInstance -Namespace root/cimv2 -Query 'SELECT DesiredSpeed, VariableSpeed FROM Win32_Fan' -OperationTimeoutSec 5 -ErrorAction Stop | Select-Object DesiredSpeed, VariableSpeed
```

5. Transcribe only outcome: class unavailable / no instances / permission denied / numeric present / invalid / ambiguous / timeout. Do not paste raw exception text (may contain machine/user details). Keep ACPI readings labeled **unattributed thermal zone**, and DesiredSpeed labeled **requested speed, not measured RPM**. Do not convert a raw number into a CPU/GPU reading without a verified unit/provider contract. No direct `_FST`, EC, bus, MSR, SMU or private-driver call is included.
6. At most two separate manual views during ordinary desktop use can note changing/unchanged values and rough elapsed time. Do not stress hardware or manipulate fan/clock/power to force a response. Unchanged values are inconclusive. Stop with unavailable/ambiguous rather than escalating access.

## 17. Recommended Step 6B.2 architecture and gates

## 18. Explicit decision and blockers

- **Proceed:** documentation, safe manual observations and existing unavailable behavior.
- **Investigate first:** GPU adapter-temperature contract through D3DKMT; ADLX as secondary documented candidate.
- **Defer:** CPU temperature, Deck fan RPM and external monitoring-provider integration.
- **Reject within current architecture:** register/bus/EC/MSR/private-driver approaches, monitoring-driver/service installation, driver replacement and automatic tool execution.

Blockers: exact installed driver/WDDM unknown; target API/metric support untested; no reliable CPU/zone or fan attribution; adapter-temperature subtype/freshness/sentinel behavior unresolved; unbounded native-call lifecycle not solved; SDK/license terms not approved; no new physical sensor acceptance. No source promises all three via one API. Confidence is high in the conservative decision, low in target compatibility. Sensors remain null and capabilities false.
