# Step 6B.6 — ADLX Rust licensing and integration clearance

Research date: 2026-11-28. Branch: `research/adlx-rust-integration-clearance`.
Decision: **B — Conditional, further clarification required.** No ADLX implementation or hardware probe is created.

## 1. Executive summary

AMD explicitly licenses its official `amd-adlx` Rust component under MIT. That grant permits use, copying, modification, publication and distribution with the required notices. It is substantive permission, not merely license metadata or an implication from public hosting. Root SDK agreement section 7 expressly recognizes component-local licenses. A Rust-only dependency and independently written loader therefore offer a plausible permissive path. This report does **not** conclude that the root agreement invalidates MIT. [L1–L3]

The combined workflow still needs clarification: SDK headers/documentation for ABI verification, public independently authored consumer source, executable distribution with MIT Rust code, and dynamic use of an existing AMD driver runtime. Root sections 1.10/3 describe broad downstream obligations; the boundary of section 7 relative to those obligations is not explicit. The installed runtime's applicable terms and trusted discovery contract were not obtained. Do **not** extend MIT to all headers, C/C++ helpers or AMD binaries. This is an engineering release decision, not a definitive legal determination. [L1, R1, R2]

The exact Rust source binds the required GPU-temperature path. It is raw unsafe FFI with write-capable APIs, not a safe read-only wrapper. Its default helper fails this project's loading and observable-cleanup requirements. Static declaration comparison is encouraging; Windows ABI compilation and target-driver compatibility remain unverified. Further research is justified; diagnostic implementation/public artifact distribution remain blocked pending scoped clearance and technical gates. Physical execution and production integration require separate authorization.

## 6. Public-source permissions

MIT explicitly covers using and modifying the official Rust component and publishing copies, with notice retention. Referencing a Git dependency does not copy SDK headers into Nepteer; it also does not erase the license obligations of code compiled into an artifact. Vendoring adds copied files and a notice-maintenance burden. Prefer an immutable Git revision in a future isolated workspace, if clearance permits, rather than vendoring or regenerating bindings. Cargo can select a package in a repository workspace; inherited edition comes from the parent workspace. No dependency, lockfile or workspace is changed here. [L2, L3, R1]

Original Nepteer source is not automatically AMD-owned or MIT-licensed merely because it calls an interface. The material issue is the root agreement's broad definition of software developed using licensed materials and whether component §7 excludes the MIT-only consumer and ABI-only header review from downstream restrictions. Public GitHub source is plausible under the MIT route; the exact combined workflow remains **Unresolved**. No claim that the absence of a project-wide license solves this issue. [L1]

## 7. Binary-distribution permissions

Compiling MIT Rust bindings into an executable is within MIT's distribution grant, subject to notices. Dynamic loading of ADLX does not stop the Rust component itself being compiled into the executable. Conversely that executable need not contain AMD runtime code. These are separate licensing layers. [L2, R1, R2]

If root §3/Schedule B applies to all of this independently authored executable, its duplication/transfer/reverse-engineering restrictions and AMD-purpose/EULA provisions could conflict with the intended public/downstream model. Whether those obligations attach to the MIT-only consumer is precisely unresolved; do not apply them universally or dismiss them. Publishing a free test artifact is still distribution. Obtain scope clarification before creating/publicly distributing the diagnostic. [L1]

## 8. Installed-runtime linking requirements

Pinned AMD Rust documentation says the library is installed with the AMD display driver and that consuming the crate needs no SDK headers/import library at build time. It supports the technical runtime-linking model; it supplies no exact installation directory or standalone runtime EULA. `amdadlx64.dll` is the x64 name, `amdadlx32.dll` the x86 name. This design only allows native Windows x86_64. Driver presence, DLL presence, runtime version and supported interfaces are independent gates. [R2, D1, H1]

No evidence establishes System32 as the required ADLX location on the Valve package. An AMD-driver-provided runtime does not imply every installed AMD DLL is an authorized substitute. Obtain the package-specific linking terms and AMD-supported trusted discovery/location contract. Missing/unsupported runtime means unavailable, never downloading, copying from another machine, changing drivers or trying elevation.

## 9. Runtime redistribution restrictions

The intended diagnostic redistributes **no AMD DLL**. The reviewed tree has no DLL/import-library payload; a source component's MIT grant cannot be used as a runtime redistribution grant. Root §2(c)'s limited sample/derivative object-code permission is not evidence that every separately installed runtime binary is redistributable. Any future bundling would require identifying its actual agreement, permitted files/versions and notices/downstream obligations. No such bundling is proposed. [L1, L2]

## 12. Unsafe API surface and caller responsibilities

Raw `#[repr(C)]` interface/vtable structs use explicit `pThis`; function pointers are unsafe. Callers must ensure correct ABI, valid aligned interface/output pointers, initialized outputs, checked result/null handling, correct interface type, bounded borrowed strings and reference lifetimes. Rust lifetimes do not tie returned pointers to the helper. There is no ownership guard automatically releasing GPU/list/service/support/metrics references. Do not allow unwinding across FFI, use-after-release, cross-thread teardown or multiple independent helpers sharing process-global ADLX state. [R1–R5]

`adlx_succeeded` accepts OK/already-enabled/already-initialized, mirroring the SDK macro. That is insufficient as a per-operation ownership/admission policy. A new isolated process should require the exact expected default-init success and treat already-initialized state as an ownership conflict, subject to verified cleanup semantics. Unknown enum/result integers must remain representable; do not transmute them into a Rust enum with invalid discriminants. [R2, R3, H1]

Write-capable surface includes tuning/fan/power setters, I²C Read/Write, display changes and performance tracking/sampling setters. Future code must place raw declarations behind a private module and expose only the fixed read path. No generic interface dispatcher, CLI method selection, logging, callbacks, tracking or setters. An MIT license is not a memory-safety or read-only guarantee. [R6]

## 13. Trusted runtime loading review

The pinned `AdlxHelper::new` calls `LoadLibraryW` on the bare architecture-specific name. Missing library returns generic ADLX_FAIL. It resolves the version query optionally and ignores its result/value, requires terminate and at least one initializer, prefers Initialize2, otherwise Initialize, and makes one initialization call with 1.5.0.124. Init2's ADL mapping is discarded. Missing required exports frees the handle. Failed/null initialization attempts termination then unload; Drop terminates and unloads, ignoring both outcomes. There is no path/authenticity/dependency policy, runtime-version enforcement or explicit observable close. [R2]

Microsoft documents application/current-directory/PATH and other loader influences, including dependencies being resolved by module name, already-loaded modules and redirection. Bare-name loading cannot establish this project's trust boundary. The pinned C/C++ platform loader's broader application/user/default/system flags also do not meet it. Checking a module's path after LoadLibrary is too late: initialization code has already executed. [H4, W1, W2]

Proposed hardened strategy, **not implemented and still gated**:

1. Obtain AMD's supported location/discovery contract for this driver runtime. Accept one fixed OS-derived protected installation location; no CLI/env/registry-user path, directory scan, working-directory/application/PATH fallback or DLL download. If System32 is later established, derive it through the Windows API; do not assume or hardcode a guessed path now.
2. Before executable loading, verify canonical local location, no untrusted reparse/redirection or user-writable ancestry/file, x64 PE identity and approved AMD/driver-package provenance. Use an explicit offline, no-UI signature/catalog policy with validated signer identity, not merely a matching filename or any trusted signature. WinVerifyTrust succeeds only on zero; catalog-signed packages may require a different documented verification flow. Unknown signer/revocation/provenance fails closed. Avoid signature-check network retrieval. [W3]
3. Resolve verify-to-load replacement risk through protected installation permissions and file-identity/handle checks; retain verification resources as appropriate. No claim of atomic handle-based LoadLibrary exists. Refuse unexpected already-loaded same-name modules and document unavoidable process/OS trust assumptions. Post-load checks are defense in depth, not the initial authenticity check.
4. Load the approved absolute path with `LoadLibraryExW` and only the reviewed dependency search flags. A protected driver directory may need `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`; a confirmed system-only layout may use SYSTEM32 alone. Exclude APPLICATION_DIR/USER_DIRS/DEFAULT_DIRS and current directory. Inventory ordinary/delay-loaded dependencies and any vendor-internal dynamic loads: top-level flags cannot prove how vendor code loads additional DLLs. Unsupported dependency trust means unavailable. [W1, W2]
5. Resolve only exact required exports, validate runtime version/contract, retain the owned HMODULE until all interfaces and initialized work are finished. Missing DLL/export, wrong machine/version or unverifiable dependencies stop without fallback. Do not initialize merely to test whether a questionable DLL is genuine.

MIT permits adapting the Rust loader with notices; alternatively write an independent private loader against reviewed Windows APIs and use only the component's raw types. A wrapper calling `AdlxHelper::new()` cannot repair its earlier load or hide termination failures. Prefer replacing/bypassing it, without copying the root-licensed C/C++ helpers. Location, signer/dependency policy and partial-init cleanup must be resolved before implementation clearance. [L2, R2]

## 15. Reference ownership and cleanup

| Resource                                      | Owner / future cleanup rule                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Library handle                                | Loader owns one acquired reference; keep loaded through all interface calls and termination.      |
| Initialized ADLX + IADLXSystem                | One process-local session; system is managed by ADLX until termination, no caller Release/delete. |
| GPU list from GetGPUs                         | Owned counted reference; release once when no longer used.                                        |
| Each GPU from typed At_GPUList                | Owned counted reference, even if rejected by selection; release once per acquired reference.      |
| VendorId/DeviceId strings                     | Borrowed for GPU lifetime; bounded private read only, no free, no use after GPU release.          |
| Performance service, support, current metrics | Each successful acquisition yields counted ownership; release exactly once in reverse-use order.  |
| Extra QueryInterface/Acquire result           | Would add ownership; avoid unnecessary calls and account for each if ever approved.               |
| Init2 ADL mapping                             | Not needed; choose legacy default Initialize path to avoid this extra lifetime contract.          |

The system-lifetime distinction is documented, not left as a generic Release requirement. Counted references must be gone before termination; calls through their vtables after unload can dispatch into unloaded code. Release returns a reference count, not ADLX_RESULT; a nonzero shared count is not automatically a leak, and zero is not a general teardown guarantee. [H2, H3, D2]

Future normal order: metrics → support → service → retained GPU references → list → termination → unload. Keep admission and loader owner alive throughout. Explicit close reports termination/unload separately; a destructor may be a last-resort returning-path guard, not evidence of successful cleanup. Error/null outputs are not assumed valid references. If initialization fails or returns already-initialized/unexpected state, determine whether termination is legal/required before coding; do not copy the helper's unconditional failure cleanup as a proven contract. If termination fails or work may still reference the library, do not unload blindly; retain it until process exit and report uncertain cleanup, without retry/reinitialization. [R2, D2]
