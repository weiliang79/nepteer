# Step 6B.4 — Standalone Windows sensor acquisition architecture

Research date: 2026-11-28. Branch: `research/standalone-sensor-architecture`.
Decision: retain unavailable production sensors; conditionally recommend one isolated ADLX GPU experiment after documentation and licensing gates. No experiment is implemented or executed here.

## 1. Executive summary

Nepteer should remain standalone. No reviewed acquisition path establishes current, correctly attributed CPU temperature, GPU temperature and measured system-fan RPM on the target. Assess each field independently. CPU and fan remain deferred. ADLX offers the strongest next GPU investigation because it documents temperature support discovery, an edge-temperature measurement and single-acquisition metrics. This is **documented generally, target unverified**, with a material license blocker; it is not approval to ship an SDK-based implementation.

Do not create a privileged component merely to fill empty dashboard values. The expected benefit of three informational metrics does not currently justify kernel attack surface, installation privileges and long-term platform maintenance. Retain null values and false capabilities rather than substitute plausible numbers, requested fan speed or unattributed zones.

## 2. Product requirement: standalone Nepteer

The released application must not require HWiNFO, Steam Deck Tools, LibreHardwareMonitor, OpenHardwareMonitor or another separately running monitor. Documented OS/vendor interfaces through an installed driver can qualify. A redistributable may qualify only with verified permission; a privileged installation is a distinct architecture requiring separate approval. Evaluate the whole acquisition chain, including any underlying driver/service, rather than only the caller's token.

Deployment classes used throughout:

| Class | Meaning                                                                                                           |
| ----- | ----------------------------------------------------------------------------------------------------------------- |
| A     | Documented native ordinary-user interface using existing OS/vendor components; no new privileged installation     |
| B     | Native interface with a bundled, licensed redistributable; no external monitor, but packaging permission required |
| C     | New driver, service, admin installation or security-sensitive hardware bridge                                     |
| D     | Independently running external monitoring application; excluded as the selected production architecture           |
| E     | Unsupported or unverifiable acquisition chain                                                                     |

These are deployment descriptions, not confidence scores. An A candidate can still be unusable on this Deck. No B component is approved for bundling.

## 5. CPU sensor candidates

No validated standalone CPU-die provider is selected. Ryzen Master Monitoring SDK is the vendor candidate, but its supported-product statement does not name Custom APU 0405. Windows thermal zones have firmware-defined identity; `Win32_TemperatureProbe` does not supply current measurements. ADLX CPU utilization does not establish a CPU temperature API. Do not use GPU edge, hotspot, SoC or APU GFX as CPU (Tctl/Tdie). [A1, A5, M1–M3]

The required CPU semantic contract must distinguish control temperature (Tctl), die temperature (Tdie), package aggregate and individual cores, including any offset and aggregation. A combined label is not a contract. Missing attribution means unavailable even with a finite Celsius value. CPU support remains unknown on the installed Valve stack.

## 8. AMD ADLX assessment

AMD currently publishes ADLX 2.0 (September 2026); core GPU temperature/metrics interfaces date to 1.0. Windows 10/11 are generally supported. Compatibility guidance excludes non-AMD GPUs and warns some legacy AMD GPUs/drivers lack support. Integrated/APU properties exist, but no complete family/driver support matrix or explicit Steam Deck LCD/Custom APU 0405 certification was found. New SDK availability does not upgrade the 2023 Valve runtime. Default initialization may refuse an incompatible driver; do not automatically use the incompatible-driver entry point. [A1–A2, A7]

The library is installed with the AMD driver; x64 header name is `amdadlx64.dll`. Presence and functionality in the user's installed package are unknown. No running AMD monitoring GUI is conceptually required. Class **A conditional on already installed compatible runtime**; B only with separate runtime redistribution permission; E for this target until demonstrated. Do not copy a DLL from another installation or change drivers to force support. No additional Nepteer driver/service is proposed, but the existing kernel display driver remains part of acquisition. No elevation requirement was found in the reviewed API contracts; that is not an ordinary-user target result. [A6–A7]

Conceptual call path: initialize → system GPU enumeration → identify one unambiguous adapter → performance service → supported GPU metrics → temperature support check → current metrics → temperature/timestamp → release interfaces → terminate. `IsSupportedGPUTemperature` reports support independently from success/failure; `GPUTemperature` describes average GPU die-edge temperature in Celsius. Hotspot and intake have separate methods. No universal numeric sentinel is adopted. Validate return status, output presence, finite/range/identity semantics separately. [A3–A4, A8]

`GetCurrentGPUMetrics` is documented for single acquisition and may take time; release its returned interface. Do not start tracking/history or change sampling intervals. `TimeStamp` describes acquisition milliseconds from “system epoch time”; the exact clock correspondence and field-level freshness on this driver need verification before computing age. It is not automatically Unix time or proof every internal sensor was freshly sampled. [A8–A9]

C/C++ interfaces are documented; Rust requires bindings. A small audited C ABI boundary or checked C-interface bindings could work, after the license gate. Do not guess vtable slots/layouts or add a crate solely because it exists. Verify calling conventions, scalar sizes, interface versions, null/error outputs and reference ownership against pinned official headers with compile-only ABI checks. ADLX also offers tuning and I²C interfaces: expose only a fixed read allowlist, no generic dispatcher, setters, tuning, callbacks, MCP server, logging or bus access. [A6–A7, A11]

## 12. Privileged driver/service architecture assessment

Architecture only: **do not implement**. A service can mediate an existing supported interface but cannot manufacture a safe hardware contract. A new kernel driver would additionally need authorized hardware communication specifications and exclusive ownership/coexistence rules. Read operations can have hardware side effects; “read-only” must apply to the complete path.

| Concern              | Minimum future evidence/design requirement                                                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Signing/distribution | Current Microsoft production signing process, certificate/account costs and release validation; signature is not security review [S1]                    |
| Secure Boot/HVCI     | Supported signed binaries, memory-integrity compatibility and HLK/Verifier testing; never require users to disable protections [S2]                      |
| Installation/removal | Explicit admin install, versioned package ownership, safe upgrade/rollback, honest reboot/pending-removal state and complete uninstall                   |
| Privilege separation | Ordinary app; narrowly scoped privileged boundary; ACL-restricted authenticated local IPC; validate caller/session, request size/version and rate        |
| Hardware operations  | Fixed validated sensor operations only; no caller-supplied addresses, IOCTLs, arbitrary buffers, mappings, bus access or writes                          |
| Identity             | Validate LCD model/firmware/interface revision; reject unknown/OLED; do not identify hardware solely by user strings                                     |
| Recovery             | Bound admission and owned requests; fail unavailable; no arbitrary retry, handle closure during I/O or claim of cleanup after a stalled driver           |
| Stability            | Kernel defects can crash the OS; a user-mode service crash still risks resource/coexistence failures; fuzz IPC and test faults before hardware           |
| Updates              | Separate Windows, firmware, display-driver and LCD/OLED compatibility matrices; signing, revocation and vulnerability response across supported versions |
| Security/anti-cheat  | Larger privileged attack surface and possible policy conflicts; no promise of universal anti-cheat compatibility or evasion                              |
| Release burden       | Hardware lab, security review, code-signing custody, support/uninstall ownership, notices and hardware-spec redistribution permissions                   |

Class C can be standalone while still imposing substantial operational/security cost. There is no trustworthy communication contract or demonstrated need sufficient to justify this route now. A privileged service, signed driver, generic hardware bridge, helper or installation script is expressly outside this milestone.

## 14. Security risks

Prefer documented getter-only APIs over new privileged acquisition. Even vendor DLL initialization may have undocumented internal work, timing or global state: audit the call path and measure its externally visible behavior before accepting a read-only claim. Secure DLL discovery must reject current-directory/search-path substitution; use only the documented installed runtime location and provenance validation, without printing private paths. Missing runtime means unavailable, not an automatic download.

Limit data collection to the three intended fields and safe version/status metadata. Keep adapter identifiers private and ephemeral. No serials, raw memory, device paths, persistent sensor logs or network monitoring. No tools are launched/reconfigured/terminated. No polling, stress load, security changes, hardware writes, drivers/services, elevation or hardware execution occurs here. Production permissions and controller lifecycle remain unchanged.

## 16. Proposed provider architecture — conceptual only

Keep the existing production implementation unchanged. A future coordinator should independently resolve battery, CPU, GPU and fan into a composed snapshot. The battery path remains the documented Windows power API. One failed backend must not fail otherwise valid fields. No backend can select mock as error recovery or silently enable another backend.

Conceptual record per field:

| Element             | Required meaning                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Capability          | Unknown / unsupported / supported for validated configuration, separately from this read's outcome                                |
| Outcome             | Available / absent / denied / invalid / ambiguous / stale / freshness unresolved / busy / provider error                          |
| Identity and origin | Approved physical quantity/site, device association, OS/vendor API, interface/runtime version; no public unique IDs               |
| Measurement         | Measured versus requested/estimated; native unit plus explicit normalized unit/value; never silently equate sensor types          |
| Time                | Provider sample time and documented clock provenance if known; local monotonic acquisition start/end and delivery time separately |
| Error               | Fixed sanitized stage/category; no raw native/provider data; cleanup outcome separate from metric outcome                         |

Provider selection must be deliberate and versioned. At most one admitted native operation per backend process, no unbounded queue or replacement workers. Dashboard/QAM share admission rather than independently multiplying vendor work. A busy field becomes unavailable/busy for that request while independently admitted battery work can complete. Share a single vendor metrics object across approved fields only when its contract supports them; do not imply simultaneous sampling across providers.

The coordinator owns bounded request tokens and provider generations, invalidates late results after selection/device/sleep lifecycle changes, and never holds application/controller/window locks during native I/O. The resource owner retains library/interface/handle lifetime until outstanding work returns; provider shutdown cannot falsely report cleanup. Cache only validated identity/support metadata with explicit invalidation, not old measurements relabeled as current. No recurring timer, automatic retry, background sample or persistent history is proposed.

## 17. Sensor attribution, freshness and future DTO review

Require a source-specific documented identity map, exactly one eligible device/sensor and independent physical acceptance. Never choose first/hottest or average disagreeing APIs. Fan tachometer zero is valid only under a measured-speed contract; undocumented zero semantics remain unresolved. Reject non-finite, sentinel, mismatched-unit or source-invalid values; no clamp/smoothing. The existing broad Celsius wrapper is representation validation, not evidence of physiological operating limits or sensor accuracy.

Preserve provider sample timestamp with its clock basis. Compute age only after establishing a trustworthy clock conversion and maximum internal sampling delay. Record acquisition latency independently with a monotonic clock. Wall-clock jumps, future timestamps, unknown epoch, missing sample time and resume/device changes invalidate age confidence. An unchanged value is not proof of a frozen sensor; repeated reads are not freshness proof.

Proposed conservative experiment policy: freshness unresolved unless a documented common clock establishes age; if established, reject negative age beyond documented clock tolerance or age over 2 seconds. This 2-second ceiling is a Nepteer proposal, not an AMD promise, and requires review against the selected runtime. A candidate with unknown age can be reported as experimental/unresolved but cannot be promoted to current production telemetry. Without automatic polling, an on-demand sample also ages while displayed; future UI/DTO review must make that visible rather than claim continuous live sampling.

Existing `Snapshot.source` identifies an entire provider, booleans conflate support with availability, `issues` is untyped, and `capturedAtUnixMs` is retrieval time. These fields cannot honestly represent mixed origins and per-field sample ages. **Recommend a separately scoped DTO/status/provenance extension before mixed-provider production integration**, preserving nullable normalized values and compatibility tests. No DTO, bindings, frontend or capability change is made now. QAM currently consumes battery/source from the same snapshot; any later display change needs its own review. [R1]

## 18. Blocking and resource lifecycle

`spawn_blocking` prevents UI-thread execution but does not cancel WMI or bound the number of blocked calls. Frontend stale-result fencing is not native cancellation. Do not add sensor work inside the existing unbounded path without reviewing this limitation. An async timeout, detached thread or dropped future cannot make a vendor DLL stop using its pointers/resources.

Future admission must remain occupied until the native owner has completed I/O and teardown. If the contract has no cancellation/deadline, a separate **ordinary-user diagnostic process** can isolate an experiment's address space, but cannot guarantee a hung kernel call terminates or that forced process exit completes vendor cleanup. No such process is created here. Any proposed production process isolation, timeout and cleanup policy requires separate approval and tests; it is not a privileged helper authorization.

Measure initialization/enumeration/acquisition/release/termination separately after each returns. Elapsed budget checks can prevent the next stage but cannot interrupt an in-progress call. Stop after a stall, crash, unexpected prompt, topology ambiguity or cleanup error. Do not reopen resources, close in-use handles or launch replacement workers. Document uncertain cleanup honestly.

## 19. Decision and rationale

Retain standalone as a product constraint, CPU/fan deferred and all three production readings unavailable. Prefer a documented vendor GPU API through existing driver components over a new hardware bridge. ADLX is the highest-confidence **conditional research candidate**, not a confirmed target provider. Its capability/identity/measurement contract improves the next question beyond repeating D3DKMT, while licensing, installed-runtime support and lifecycle remain real blockers.

No candidate currently passes all production gates. Do not trade the open-source-oriented release model for SDK convenience without an explicit product/license decision. Do not select HWiNFO as a mandatory fallback. No privileged component is justified at this stage.
